# Callout colour and the nesting invariant

**Backgrounds are painted as translucent tints, never as the authored hex, and that is load-bearing.** Obsidian gives nested callouts their stepped look purely by compositing — core paints `color-mix(in oklch, var(--callout-color) 10%, transparent)` under `mix-blend-mode: darken`/`lighten`, so each level lays another layer over the one beneath it and the group alpha climbs as `1 - 0.9ⁿ`, unbounded in depth. An opaque fill hides what is behind it, and `min(x, x) = x` makes the step *exactly* zero. **CSS cannot count nesting depth** (a self-incrementing custom property is a dependency cycle, `:has()` is a predicate not a counter, `counter()` only reaches `content:`), so an explicit per-level rule can only ever approximate a few levels — one was written and deleted for that reason. Translucency is the only real answer.

`translucentTintFor` (`utils/colorUtils.ts`) solves `alpha * colour + (1 - alpha) * backdrop === authored` per channel, so the callout renders *identically* on its own and only what shows through it changes. `minTintAlpha` is the smallest alpha that keeps the solved colour in gamut, and a gradient's two stops share one alpha since ramping it would tilt the sweep. There is **no opt-out** — a flat fill breaks nesting for everything stacked inside it, so the `solidBackground` flag that used to offer one was retired (`CalloutRegistry.dropSolidBackgroundFlags()` deletes it from old data; `importValidator`'s `RETIRED_FIELDS` drops it from old export files without warning).

**Which alpha, though, is a real choice, and `utils/bgTintAlpha.ts` owns it.** Every alpha at or above the minimum renders the callout *itself* identically — the source is re-solved along with it — so what the choice decides is everything stacked inside: depth `n` renders `S + (1 - alpha)ⁿ·(backdrop - S)`, converging on the source, which sits `‖bg - backdrop‖ / alpha` from the page. Taking the smallest viable alpha, as the plugin once did unconditionally, buys the boldest step per level (`(1 - alpha)·(bg - backdrop)`) and pays for it with a wildly saturated source — which is what "my nested callouts are unreadable" reports were about. One cap raises the floor: `accentAnchorAlpha` (never end up more intense than the callout's own accent, measured as one distance from the backdrop, never per channel — a channel where the accent sits a few levels from the page has a near-zero denominator and turns hex rounding into a demand for alpha 1.5). **It is a preference, not a constraint.** A cap handed to `resolveTintAlpha` beside the real minima returns null above the ceiling — and null is the opaque fallback, so a cap meant to protect nesting would be destroying it; a background bolder than its own accent genuinely asks for 0.75 and simply cannot have it, so the cap is dropped and the colour's own minimum stands. A gradient's far stop is anchored against its own `textToColor*`, never against the primary accent, which is a deliberately different hue and so says nothing about how intense that stop may be.

**Nothing bounds nesting *depth*, and that is a decision, not an omission.** The alpha above can act only through a `background-color` this plugin emits, and it emits none for an untouched built-in — deferring to the theme is the point — so core's `1 - 0.9ⁿ` ladder still runs on exactly the callouts most people have. Bounding it needs a `.callout .callout` rule restating core's tint with the page colour pre-mixed in, and that is dilution with `--background-primary` by construction: the stack stops piling up and every level comes out desaturated instead of staying itself. Fixing the colour the ladder converges *on* is the version that leaves core's compositing untouched.

**An unmodified built-in gets no `--callout-color` at all** (`CSSInjector.accentProps` + `CalloutRegistry.isUnmodifiedBuiltIn`), so core's rule — and any theme overriding it — keeps deciding the accent. `--cs-accent` is the plugin's own accent variable and is **always a real colour on every Obsidian version**, which is why it, not `--callout-color`, is what our `color-mix()` calls read: core's variable is a bare RGB triplet on ≤1.12 and a full colour on 1.13+. For an untouched built-in it follows core's own variable via `OBSIDIAN_CALLOUT_VAR` (`constants.ts`) — through `--cs-accent-theme`, registered `<color>` in `styles.css`, which is what makes "always a real colour" enforced rather than merely intended: a theme written for ≤1.12 still hands 1.13+ a bare triplet, and without the typed hand-off that value reaches `color-mix()` and drops the whole declaration. Note this hardens *our* surfaces only; core's own rule reading the same bad theme value is the theme's bug, and reproduces with the plugin disabled. `--cs-color-rgb` is legacy, kept one release for external consumers, and nothing here depends on it. The fallback block passes `imposed: true` because its job is to paint callouts *other* than the one it copied — omitting `--callout-color` there would silently disable the setting.

Two migrations keep old data from re-breaking this: `CalloutRegistry.dropDerivedBackgrounds()` retires a stored background that `derivedBgAmount` can show IS just the accent tinted, and `CalloutEditorSave` stops writing one back. The editor form always holds a concrete background (a swatch must show something) — persisting it unconditionally is what turned every callout the user merely opened into an opaque one.
