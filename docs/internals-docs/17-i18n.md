# Localization

The plugin ships a UI in 32 languages. This document covers how strings are
declared, resolved, downloaded, cached, and verified -
[`src/i18n/`](../../src/i18n/), plus [`scripts/generate-locales.mjs`](../../scripts/generate-locales.mjs).

## Two identifier spaces, kept apart on purpose

- A **locale code** is what the user or Obsidian names a language:
  `"he"`, `"zh-tw"`, `"no"`. Several codes can mean the same underlying
  translation.
- A **locale file id** is one body of strings - one source module
  (`src/i18n/he.ts`), one generated JSON file (`locales/he.json`), one
  download, one on-disk cache entry.

```ts
LOCALE_FILES: Record<string, LocaleFileId> = {
  he: "he", zh: "zh", "zh-tw": "zhTW", "zh-hk": "zhTW", "zh-sg": "zh",
  no: "nb", nb: "nb", ...
}
```

> [!IMPORTANT]
> **A locale *code* is not a locale *file*.** 34 codes map onto 31 files.
> Norwegian's `nb`/`no` collapse to one file; Hong Kong Chinese (`zh-hk`)
> and Traditional Chinese (`zh-tw`) both serve from `zhTW`. This is why
> picking Norwegian Bokmål or Hong Kong Chinese in the picker downloads
> **nothing new** if the shared file is already present - and why
> `registerLocaleFile(file, strings)` registers the loaded table under
> **every code that file serves**, not just the file's own name: registering
> under `zhTW` alone would leave `"zh-tw"` and `"zh-hk"` silently resolving
> to English with the correct translation sitting right there in memory.

`setLocale` (which picks a *table to render*) and `resolveLocaleFile` (which
picks a *file to download*) both funnel through the exact same `resolve()`
helper - if the two disagreed, the plugin could fetch one language and
display another.

Locale membership uses own-property checks. A malformed saved preference such
as `__proto__` or `constructor` falls back to English and never becomes a
download filename or an invalid locale passed to number formatting.

`"auto"`, the saved default, resolves through Obsidian's own interface
language, which comes from `getLanguage()`. It is never moment's global
locale: Obsidian points moment at its language on launch, but other plugins
re-point it for their own date formats (Calendar's "Override locale" does), and
reading moment made "follow Obsidian" follow them instead. Before 1.8.7 moment
was the fallback; the plugin's minimum is now 1.13.4, so it is gone. The lookup
never throws: it runs in `onload` before anything is registered, and an error
there would cost every callout its styling.

`getLanguage()` returns Obsidian's own codes. Most resolve as they are: `no`,
`zh`, `zh-TW`, `pt-BR` and `en-GB` all fall through the chain above. `cz`,
which an older Obsidian may have saved for Czech, is renamed to `cs` first,
the way Obsidian renames it for moment. The API reads the setting live, so
between a change in **Settings → General** and the relaunch Obsidian asks
for, it already names the new language. Obsidian's own dropdown does the same.

## `t()` - the translation function

```ts
t(key: string, vars?: Record<string, string | number>): string
```

Resolution: **active locale table → English → the key itself** - a locale
that's absent, stale, or only half-translated degrades one string at a time
rather than breaking. `{{placeholder}}` interpolation is done with a
**function** replacer, never a string one:

> [!WARNING]
> `String.prototype.replace` reads `$&`, `` $` ``, `$'`, `$$`, `$1` etc. as
> *patterns* when the replacement argument is a string. Almost every
> `{{name}}` interpolated in this plugin carries text the **user typed** - a
> callout's display name, a filename, an icon name. A callout literally
> named `A$&B` would come back as `A{{name}}B` (`$&` re-inserting the whole
> matched token) if `t()` used a string replacement; one named `$$` would
> collapse to a single `$`. `t()` passes a **replacer function** instead,
> which receives the value verbatim and substitutes nothing else.

### Keys built at runtime

A few call sites build the key instead of naming it -
`` t(`colorName.${key}`) `` - so searching the source for `colorName.teal`
finds only the locale tables. Those keys are **not** unused, and a cleanup that
deletes "keys with no reader" must leave them alone. Each hole is filled from a
list in the code:

| Key family | Values come from |
|---|---|
| `recovery.details.field.*` | `FIELDS` (`recoveryDetailFields.ts`) and `SIDES` (`recoveryValues.ts`) |
| `recovery.details.count.*`, `recovery.details.calloutState.*` | `RecoveryItemKind` |
| `iconPicker.cat.*` | the categories packed into each bundled icon index |
| `colorName.*` | `COLOR_ANCHORS` (`colorNames.ts`) |
| `iconPicker.materialWeight*` | `MATERIAL_WEIGHTS` (`recoveryValues.ts`) |
| `portable.before`, `portable.after` | the diff rows in `portableConversionRows.ts` |

`tests/i18nDynamicKeys.test.ts` reads those same lists and fails on a value
with no English key (the UI would show the raw key) and on a key under an owned
prefix that nothing reaches (dead - delete it everywhere). It also fails on a
new key-building template it doesn't know, so add a row to its `FAMILIES` and
to this table together. Regenerating the icon packs is the usual way to trip
it: an upstream category added or dropped shows up here by name.

## Only English is bundled

Every other locale is a downloaded JSON file, cached under
`<plugin-dir>/translations/<file-id>.json`. This is a deliberate size
trade-off: shipping all 32 languages inside `main.js` took it from 1.70 MiB
to 3.70 MiB - esbuild emits ASCII-only output, so every non-Latin character
became a 6-byte `\uXXXX` escape, multiplying the cost of every non-English
string several times over.

### `LocaleStore` - download, verify, cache

[`src/i18n/LocaleStore.ts`](../../src/i18n/LocaleStore.ts), structurally almost
identical to `PackDataStore` (see [Icons](13-icons.md)) but with one
deliberate difference, covered below.

```ts
prepare(pref): Promise<LocaleDiskResult | null>   // disk only, NEVER fetches - called once at startup, blocking
ensure(pref): Promise<boolean>                       // read cache, fetch only if missing/stale - background
```

- **`prepare()`** is the one blocking locale step in `onload()` - a single
  disk read of an already-present ~50 KB file, never touching the network.
  It has to finish before the first translated string of the session
  renders. See
  [Plugin lifecycle § step 7](03-plugin-lifecycle.md#startup).
- **`ensure()`** is called later, in the background, and is the single entry
  point for **both** callers that might need a download - the startup pass
  and the language picker - "because the decision of whether a download is
  needed belongs here, not in the UI."

### Locale file staleness vs. a corrupt icon pack

> [!NOTE]
> **A checksum mismatch on disk means something different for a locale
> than for an icon pack, and the two are handled oppositely on purpose.**
> `LocaleStore.loadFromDisk` treats a hash mismatch as **`"stale"`**: almost
> always just an older-but-still-valid copy of the translation, downloaded by
> a previous version of the plugin before new strings were added. It's
> **registered and used immediately** (the user sees their own language at
> once, offline, with `t()` filling any new keys from English), while a
> background refresh silently upgrades it. `PackDataStore`, in contrast,
> treats an icon pack's checksum mismatch as `"corrupt"` and **rejects it
> outright** (see [Icons](13-icons.md#packdatastore---bundled-file-download-and-verification))
> - because an icon pack's hash only ever changes when its *contents* are
> refreshed with a new pinned tag, so a mismatch there means edited or
> damaged data, never "an older but fine" copy.
>
> Strict rejection is reserved for **the network only** - an unverifiable
> *download* is discarded outright, same as a pack. The plugin's own folder
> on disk is treated as already as trusted as `main.js` sitting right beside
> it; the shape check (`parseLocaleFile`) is the entire remaining attack
> surface, and translations are only ever inserted as **text nodes**, never
> parsed as markup, so there's nothing else to sanitize.

### The URL is pinned to the running plugin's *version*, not a frozen tag

```ts
localeUrls(id, version) = [
  `https://cdn.jsdelivr.net/gh/${REPO}@${version}/locales/${id}.json`,
  `https://raw.githubusercontent.com/${REPO}/${version}/locales/${id}.json`,
]
```

This is the **opposite** choice from icon packs (pinned to the frozen
`packs-v3` tag - see [Icons](13-icons.md)), and deliberately so: the
version-pinned URL means a release that adds or changes UI strings needs
**no separate tag work at all** - the release tag already exists the moment
the version is cut, so publishing new translations is free. Icon packs are
megabytes that almost never change, so a stable, permanently-cached tag is
right there; locale files are kilobytes that change on most releases, so
pinning to the ever-advancing version number is right here.

> [!NOTE]
> **A build made between releases points that URL *behind* itself.**
> `npm run dev` and `npm run build` regenerate `src/i18n/localeManifest.ts`
> and bake it into `main.js` on every run; `manifest.json`'s `version` only
> moves when a release is cut. So any build from `master` after the last tag -
> every local dev build, every pre-release install - carries a manifest that
> expects the `locales/*.json` in the working tree while `localeUrls()` still
> resolves to the **previous** tag's older JSON. Every non-English download
> then fails its checksum on both mirrors:
>
> ```
> [CalloutStudio] locale "he" mismatch from https://cdn.jsdelivr.net/gh/Niv20/obsidian-plugin-callout-studio@2.11.0/locales/he.json
> [CalloutStudio] locale "he" mismatch from https://raw.githubusercontent.com/Niv20/obsidian-plugin-callout-studio/2.11.0/locales/he.json
> [CalloutStudio] locale "he" download failed undefined
> ```
>
> `download failed undefined` is not an exception - both mirrors returned
> `200`, the bytes just didn't match the baked-in `bytes`/`sha256`. The UI
> stays as it was and a notice says the language could not be downloaded, with a **Retry** button.
>
> This is expected, affects only pre-release builds, and clears itself the
> moment the next version is tagged - the CI locale-sync gate
> ([below](#contributing-translations---the-workflow-this-enforces)) guarantees
> the tag's JSON matches that release's compiled manifest. The only way it
> reaches a released user is a release whose regenerated `locales/` +
> `localeManifest.ts` weren't committed at the tagged commit - precisely what
> that gate prevents.
>
> To exercise a non-English UI in development, seed the on-disk cache by hand.
> `LocaleStore` reads `<plugin-dir>/translations/`, and in a dev checkout the
> plugin dir *is* the repo, so the already-matching file is one copy away:
>
> ```
> cp locales/he.json translations/he.json   # translations/ is gitignored
> ```
>
> Reload; the copy verifies fresh against the dev manifest and renders with no
> network call.

### What happens when a translation download fails

Nothing breaks. English is always a complete, working UI - a failed download
(offline, CDN blocked) leaves the interface as it was and the plugin tries
again automatically on the next launch.

A language picked in the footer's globe is told in **notices**
(`downloadLanguage` in `settings/sections/languagePicker.ts`), never in a row of
the page:

1. A language already on the device switches at once with no notice. A copy
   cached by an earlier session counts: the pick first reads it from disk
   (`LocaleStore.prepare`), so only a language that really has to be fetched
   gets a notice.
2. Otherwise a `workNotice` says **Downloading translation…**
   (`locale.downloading`) with the painting brush, like **Scan for callouts**:
   up for one whole stroke at least (`WORK_ONE_PASS_MS`) however fast the fetch
   is, then a pause (`BEFORE_RESULT_MS`) before the result, so each can be read.
3. The result is a success notice (`locale.downloaded`), or, if `ensureLocale`
   says the language did not arrive (or threw), a problem notice
   (`locale.notDownloaded`, naming the language the way the picker shows it)
   with a **Retry** button that fetches again. Picking the same language again
   from the globe retries too. One fetch per plugin at a time; a second press
   does nothing.

The background fetch at startup stays silent, as before. What tells the user is
the settings: each time the tab opens (`beginVisit` in
`declarative/declarativeSettings.ts`), if the chosen language is still not on the
device and is not downloading, `tellMissingLanguage` shows the same
`locale.notDownloaded` notice with **Retry** (a `warning`, where a fetch that
just failed is a `problem`). Every failure along the way
(disk-write, checksum, mirror exhaustion, malformed file) also gets a
`console.warn` for whoever is diagnosing a report - see
[Logging and diagnostics § locale downloads](24-logging-and-diagnostics.md#locale-downloads---consolewarn)
for the full list.

## Surfaces that snapshot translated text and need a manual refresh

Most of the UI calls `t()` while it draws, so it picks up a new locale for
free the next time it re-renders. Several surfaces **cache** rendered text and
need `plugin.applyLocaleChange()` explicitly, called both when the user
picks a language and when a background download lands mid-session:

1. **The open settings tab** - `settingsTab.update()`, which Obsidian turns
   into a redraw of the open page (nothing when the tab is closed).
2. **`refreshFixedCommandNames()`** - the built-in commands' palette
   labels. Obsidian snapshots a command's name at `addCommand()` time and
   never re-reads it, so a locale arriving after startup leaves the palette
   in the old language until this re-registers each command **at the same
   id** (preserving the user's hotkey - see
   [Editor integrations](10-editor-integrations.md#built-in-commands-and-availability)).
3. **`refreshRenderModes()`** - the heading-fold chevron's tooltip is baked
   into a CodeMirror widget at build time and needs the widget rebuilt to
   pick up new text.
4. **`refreshOccurrencesViewLocale()`** - redraws open occurrence sidebars
   and refreshes the `show-callout-occurrences` command at its stable id.
   Before view registration, this is a no-op.
5. **`refreshPortableConversionViewLocale()`** - redraws open Markdown-conversion
   review sidebars while retaining their current selection and recovery state.
6. **The persistent missing-settings startup notice** - its message and settings
   link are updated in place. It is registered only after recovery has loaded
   the saved language preference and cached locale setup has finished; creating
   it inside `loadSettingsInto()` would snapshot English before that setup.
   A later locale download updates the same nodes without reopening a dismissed
   notice. Unload disposes its status subscription and hides it.

## Contributing translations - the workflow this enforces

`CONTRIBUTING.md` is explicit: **only `en.ts` is hand-maintained as the
canonical source.** The other 31 files were
machine-translated and "almost certainly have rough edges somewhere" - fixing
a wrong or awkward string in one of them is a low-effort, code-free PR. When
adding or changing a string, **only touch `en.ts`** and don't re-translate
the other 31 on every small edit; wait until the wording is settled, then
translate.

> [!IMPORTANT]
> **Generation is not optional, and it's not a manual step someone has to
> remember.** `npm run i18n:generate` runs automatically as `prebuild`
> (unlike `icons:generate`, which is deliberately manual - see
> [Build, test, and release](20-build-test-release.md)) - it's local,
> touches no network, and finishes in well under a second. **Both CI
> workflows re-run it and fail on any `git diff`** against what's committed
> under `locales/` and `src/i18n/localeManifest.ts`. A stale manifest would
> fail every download's checksum for that release, so there's no path to
> shipping one.

### When "only touch `en.ts`" is not enough: retiring a stale translation

`t()` resolves *active table → `en` → the key itself*, so a locale that still
carries a key **wins over English**. Editing `en.ts` alone is therefore the
right move only while the translated value stays *true*. When a change makes it
false, leaving it in place ships the bug to every non-English user.

`welcome.sample` is the worked example. Its earlier translations hard-coded
`[!tip]`, `[!warning]` and `[!note]` - the very built-ins the splash stopped
using, because a theme restyles them by name. A translated splash showing the
old, theme-hijackable sample was worse than an untranslated one showing the
correct sample, so the stale entries were **deleted** until they could be
retranslated. All 31 locale files now have the revised sample with `{{id}}`.

Deleting is the move, not renaming the key: an entry a locale carries and `en`
does not is an *orphan*, and `tests/localeContent.test.ts` fails hard on those.
Deleting is safe in the other direction - the missing-key check is deliberately
diagnostic and gates on nothing.

The same test suite is what forces the decision rather than letting it slide:
`{{placeholder}}` parity against English **is** enforced, so a new
interpolation in `en.ts` (here, `{{id}}`) fails the build until every locale
either gains it or gives the key up.

A punctuation-only edit is the opposite case. Putting an ellipsis on an English
label, or taking it off (see [Button labels and the
ellipsis](16-settings-ui-and-modals.md#button-labels-and-the-ellipsis)), leaves
every translation true, so nothing is retired. Each language lines up in its next
pass, and until then `t()` returns the locale's own punctuation for that key.
